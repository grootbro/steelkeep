# Notifications

Configuration → Notifications manages installation-wide channels for new backup and restore outcomes. Supported channel types are SMTP email, Slack webhook, Discord bot, Discord webhook, Microsoft Teams webhook, Telegram, Pushover, Gotify and a generic JSON webhook. Each channel has success/failure policies and a separate automatic-delivery switch, disabled by default. Failure includes failed, interrupted and cancelled operations. Creating, enabling or editing a channel does not replay historical jobs.

`read` can inspect public channel configuration, delivery records and attempt details. `configure` is required to create, edit, remove, test or retry a channel. REST, OpenAPI and MCP expose the same services. Credentials and sensitive destination URLs are sealed at rest, omitted from public responses and never echoed into the editor; blank secret fields preserve existing values. Editing uses the current channel revision. Removing a channel preserves delivery history.

An explicit **Send test** queues a real outbound message even if automatic delivery is disabled. Its returned delivery ID establishes acceptance into Steelkeep's queue. Only the worker contacts providers. `succeeded` means the provider accepted the request or SMTP recipients, not that a recipient read the message. **Details** preserves previous attempt errors after a later retry succeeds.

Terminal transitions enqueue notifications atomically with job metadata. There is no historical scan/backfill. Configuration changes cancel unstarted old-revision deliveries rather than redirecting them to a new destination. A worker epoch fences claims; a restarted in-flight send becomes `uncertain`, because the provider may already have accepted it. It is never silently replayed. An explicit retry of an uncertain delivery requires duplicate-risk confirmation. Known temporary refusals receive bounded retries; test and retry requests reuse their original actor-scoped keys after ambiguous responses, authentication errors or rate limits.

Outbound hosts must be in `STEELKEEP_ALLOWED_HOSTS`. HTTP redirects are refused, responses are bounded to 64 KiB and provider diagnostics are replaced with safe errors. SMTP uses Nodemailer 10.3.1 with verified implicit TLS or required STARTTLS, bounded connections and absolute cancellation. Plain SMTP is permitted only for loopback fixtures. Provider credentials belong in the channel form, not the host allowlist, URL query of Steelkeep itself or agent prompts. All channels are currently global to the installation; source-specific routing is not implemented.

## Evidence and limits · 31 October 2026

The isolated schema-9 proof passed 1 test / 94 assertions with actual PostgreSQL, 11 loopback HTTP sends and 3 loopback SMTP sends under Bun. It checked terminal-only queueing, no replay after enable/edit, secret preservation, CAS, scope enforcement, REST/MCP, per-attempt history, bounded HTTP retry, redirects, uncertain acknowledgements and epoch recovery. Its database, synthetic sinks and temporary keys were removed. A separate stalled-SMTP test proved that cancellation destroys an active socket rather than waiting for the provider. Real provider accounts and SMTP TLS handshakes remain unqualified.

Intercepted frontend proofs cover channel CRUD, permission restrictions, secret omission, CAS draft preservation, stable test/retry keys through 503/403/429, duplicate-risk acknowledgement, read-only attempt details and mobile layout. These are UI wiring checks, not delivery to external services. No external message was sent during development.

The main local metadata was migrated to 9 after stopping idle application processes and retaining a private 167,432-byte metadata backup. All 20 plans remained keep-all/cleanup-disabled and all 28 artifact records active. The restarted API returned zero notification channels and deliveries, so migration sent nothing. Development mounts the pinned 1.76 MB pure-JavaScript SMTP package read-only into the existing API/worker image; no image rebuild or pull was performed for this slice. Immutable package qualification remains a separate checkpoint.
