# Steelkeep: fresh technical research, 31 October 2026

Research only. No product/browser UI, services, containers, installs, builds, tests, lint, or typechecks were run. The only authored file is this report. Recommendations below are design proposals, not validated implementation or a support guarantee. Implementation was being edited concurrently; file observations describe the snapshot read during research.

## Five practical findings

1. **Keep pg-boss and the application operation ledger.** The installed 12.38.0 already supplies transactional Kysely integration, leases, retries, and cancellation signals. A queue cannot make an external database restore exactly once. Keep execution fencing, immutable artifact keys, target reservation, and the `interrupted` outcome; combine queue cancellation with domain cancellation. Do not migrate to Temporal for the current single-installation workflow. [pg-boss workers](https://pgboss.io/api/workers), [transaction adapters](https://pgboss.io/api/adapters).
2. **Make engine support a capability profile with real prerequisites.** PostgreSQL, MySQL, MariaDB, MongoDB, SQLite, Redis, ClickHouse, and SQL Server need different consistency and target-access mechanisms. ClickHouse native backup is viable through a configured backup disk plus a shared filesystem; SQL Server BACPAC import fits an existing empty target but has a source-quiescence requirement. A dropdown value cannot establish either capability. [ClickHouse local disk](https://clickhouse.com/docs/concepts/features/backup-restore/local-disk), [SqlPackage import](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-import?view=sql-server-ver17), [export](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-export?view=sql-server-ver17).
3. **Use the actual 2026 MCP contract.** The official latest revision is **2026-07-28**. Tasks and Skills are opt-in extensions. Installed SDK 2.4.0 already supports the new revision and Skills; the Skills attachment API remains explicitly experimental. Keep durable job IDs and polling as the baseline; add extension adapters over the same services rather than creating another job engine. [Specification](https://modelcontextprotocol.io/specification/2026-07-28), [SDK 2.4.0](https://github.com/modelcontextprotocol/typescript-sdk/releases/tag/v2.4.0).
4. **TanStack DB is now a release candidate even though npm calls it `latest`.** Keep the explicitly requested stack, pin the compatible versions, and use request-local clients if authenticated data participates in SSR. Do not queue restore commands through an optimistic/offline mutation layer. [TanStack DB SSR](https://tanstack.com/db/latest/docs/guides/ssr), [query collection](https://tanstack.com/db/latest/docs/collections/query-collection).
5. **Reference fidelity needs source composition, not a new UI framework.** Databasement uses Blade/Mary/daisyUI and Chart.js; Salt uses React/Mantine. Reproduce Databasement's operational hierarchy, density, typography, tables, and restrained charts in the existing React/CSS components. Preserve MIT adaptation attribution; use Salt's interaction ideas without copying its AGPL implementation. Native dialogs and tables can cover the current product; one unstyled primitive library is a later option for genuinely complex menus/comboboxes.

## Durable execution: what the queue does and does not solve

**Source evidence:** pg-boss can atomically enqueue through the existing Kysely transaction. Its current workers expose per-job abort signals for expiry/shutdown/lost claim. A failed database heartbeat does **not** itself abort the job. Its transactional worker mode keeps one SQL transaction open for the handler and is documented as suitable for work lasting seconds, not long jobs. [Adapters](https://pgboss.io/api/adapters), [worker behavior](https://pgboss.io/api/workers).

**Recommendation:** preserve Steelkeep's independent operation status/phase/heartbeat and native-process ownership checks. Use queue delivery as a wake-up mechanism, not authority to replay a restore. A queue signal should join the existing cancellation signal; domain DB connectivity loss should still stop/fence execution. Do not put a two-hour dump/upload inside a metadata transaction. A queue lease cannot fence a database server already executing a command.

Persist intent before external writes, distinguish known failure from unknown outcome, and publish artifacts only after verified completion. Retries can use new immutable keys for safe backup attempts; restore retries after possible writes remain forbidden. For native server jobs, reconcile by their recorded identity before deciding whether the target is safe. Never show a fractional progress percentage unless native evidence supports it.

**Source evidence:** Temporal documents idempotent activities and retry behavior; durable execution does not remove the need for an idempotent external write boundary. **Recommendation:** reconsider it only if Steelkeep grows into distributed agents, cross-host orchestration, multi-stage PITR drills or approval waits that become awkward as explicit application state. No replacement is justified by the current scope. [Temporal activity definition](https://docs.temporal.io/activity-definition).

## Actual backup/restore profiles for all eight engines

These are implementable native approaches, **not claims that Steelkeep has passed them**. Each engine needs a real synthetic dump → upload → download → restore → data-verification slice through UI and MCP when runtime work is authorized. Support must name tested server/tool versions and topology, not “all versions.”

| Engine | Native method and source consistency | Safe target/validation contract and initial limit |
| --- | --- | --- |
| **PostgreSQL** | `pg_dump` custom archive; an exported transaction snapshot can align the data manifest with the dump. Native logical export is single-database, not cluster globals or PITR. [Official pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html). | Distinct empty DB, native `pg_restore`, schema/data verification; record roles/extensions/large-object coverage. Sequence state is not equivalent to MVCC row state, so report its policy separately. Keep explicit version compatibility; worker client 17 does not establish server 18/19 support. |
| **MySQL** | `mysqldump --single-transaction --quick` for transactional tables. This does not make nontransactional tables safe or isolate concurrent DDL. [MySQL 8.0 manual](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html). | Start with InnoDB, known version pair, controlled DDL and verified empty target. Triggers/routines/events/views are separate coverage decisions, never silently omitted while claiming a complete DB backup. Align the validation manifest with the same consistency mechanism. |
| **MariaDB** | Use `mariadb-dump` and matching MariaDB restore client. Modern dumps contain a sandbox-mode command that older/MySQL clients do not necessarily understand. [MariaDB manual](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump). | Separate profile from MySQL, with engine/client checks. Same InnoDB/DDL caveats. Do not assume swapping a binary name gives bidirectional MySQL/MariaDB portability. |
| **MongoDB** | `mongodump --archive`/`mongorestore`; consistency under writes requires deliberate topology handling. `--oplog` is for a **full replica-set-member dump**, cannot combine with `--db`, and does not work for sharded-cluster backup. [mongodump](https://www.mongodb.com/docs/database-tools/mongodump/). | Initial real slice: one quiet database into a distinct empty database, compatible server/FCV, verify BSON types, indexes/options and documents. A later full replica-set profile needs empty isolated instance semantics and oplog replay; do not advertise `--db --oplog`. Credential YAML via `--config` avoids a password-bearing URI in argv. |
| **SQLite** | Online Backup API or `VACUUM INTO` makes a consistent separate database file; copying an active `.db` alone is unsafe in WAL situations. [SQLite backup](https://www.sqlite.org/backup.html). | Worker-local explicitly allowed file roots; reserve a separate target path, reject symlink/path escape and nonempty target. Run `integrity_check` **and** `foreign_key_check`, then fixture/schema checks. The first does not check foreign-key violations. [Pragmas](https://www.sqlite.org/pragma.html). |
| **Redis** | `redis-cli --rdb` downloads a native point-in-time full-instance snapshot. RDB is an actual backup format; logical `SCAN`/`DUMP` loops do not establish a consistent full instance. [Redis CLI](https://redis.io/docs/latest/develop/tools/cli/), [persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). | Initial real RDB restore needs a provisioned isolated target instance and server-local artifact placement/start lifecycle, not just a remote Redis URL. Never `FLUSHALL` to make a target “empty.” Verify types, values, module compatibility, and expiration semantics relative to the snapshot/validation time. Standalone full instance first; cluster shards and modules require separate acceptance. |
| **ClickHouse** | Native `BACKUP DATABASE ... TO Disk('backups', '<unique>.zip')`; configured backup disk and allowed path; native `RESTORE DATABASE source AS target`. [Local disk](https://clickhouse.com/docs/concepts/features/backup-restore/local-disk). | Start single-node ordinary MergeTree tables, reserved precreated empty target, matching DB definition and worker/server shared spool. Keep `allow_non_empty_tables` disabled. Compare schema and exact synthetic data; no unproven cross-table transactional snapshot claim under writes. Distributed/replicated/external-table behavior is a separate profile. |
| **SQL Server** | Native `.bak` is preferable for full recovery, but restoring another DB over a precreated target conflicts with the family-GUID safeguard without `REPLACE`. BACPAC is a workable **logical portability** profile when source writes are stopped or export comes from a consistent copy. [RESTORE safety](https://learn.microsoft.com/en-us/sql/t-sql/statements/restore-statements-transact-sql?view=sql-server-2017), [SqlPackage export](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-export?view=sql-server-ver17). | Import officially accepts an existing DB containing **no user-defined schema objects**. No drop/REPLACE/source overwrite. Verify data/schema and supported object types; BACPAC is not a native disaster-recovery backup or log chain. x64 optional worker profile; see packaging details below. [Import](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-import?view=sql-server-ver17). |

**Recommendation:** add explicit manifest fields for `format`, tool/server version, engine/topology profile, consistency method, included/excluded object classes, snapshot/native operation identity, and validation evidence. A successful artifact upload, a content checksum, an engine structural check and a fixture-data restore are four different facts. The UI and tool result should preserve that distinction.

Large-database validation needs a documented budget: streaming digests/counts and bounded schema metadata instead of retaining all rows in application memory. A source manifest must correspond to the captured snapshot; “counts before and after match” is not proof that no changes occurred.

### ClickHouse packaging: shared disk works, but it is not generic remote support

**Source evidence:** the backup disk is configured inside ClickHouse, with allowed disk/path configuration. Native backup can produce zip files, rename databases on restore, and run asynchronously. Nonempty-table restore is an opt-in setting that can duplicate data. Named collections can keep S3 credentials out of queries/logs. [Disk setup](https://clickhouse.com/docs/concepts/features/backup-restore/local-disk), [overview and named collections](https://clickhouse.com/docs/concepts/features/backup-restore/overview).

**Recommendation:** root's proposed local-disk profile is sound as a scoped design: configure one server backup disk; assign an unpredictable operation-owned filename; grant the worker access only to the spool; wait for native completion; hash/upload using Steelkeep's existing S3 client. On restore, download/verify to the target's mapped spool before issuing the renamed native restore. Avoid embedding S3 credentials in SQL. Do not log raw queries/responses, because identifiers or server errors can still expose sensitive context.

Persist native operation IDs and use `system.backups`/configured backup history to reconcile. Losing an HTTP connection does not establish cancellation or failure of server-side work. If the native outcome cannot be resolved, keep the restore target blocked. For truly remote ClickHouse hosts without shared storage, provide a separately configured named collection or transfer agent later; do not pretend the server-local file exists on the worker. [Native backup state](https://clickhouse.com/docs/reference/system-tables/backups).

### SQL Server packaging: the honest safe profile

**Source evidence:** Microsoft's restore safeguard compares database family GUIDs; empty does not exempt a precreated target from being a different database. `RESTORE VERIFYONLY` checks readability/completeness and available checksums but explicitly does not validate data structure by performing a restore. [RESTORE](https://learn.microsoft.com/en-us/sql/t-sql/statements/restore-statements-transact-sql?view=sql-server-2017), [VERIFYONLY](https://learn.microsoft.com/en-us/sql/t-sql/statements/restore-statements-verifyonly-transact-sql?view=sql-server-ver17).

**Recommendation:** do not bypass the product rule with `WITH REPLACE`, target drop/recreation, or a misleading native-backup label. Under the current precreated-empty-target rule, implement a clearly named BACPAC profile, enforce/document controlled source quiescence and the tool's supported object coverage, then actually import into the isolated empty target. Quiescence cannot be proved by equal row counts before/after. A native full/log restore profile can be added later if the target contract deliberately supports a separately reserved **absent database name and new file paths**; it must remain distinct from overwriting an existing target.

**Source evidence:** SqlPackage 170.5.96 is documented for Linux **x64**, with .NET 10 recommended; its standalone download avoids a separately installed runtime but still needs OS dependencies. Microsoft does not support SQL Server container emulation on ARM hosts. Do not infer Linux ARM64 support from the fact that .NET itself supports ARM64. [SqlPackage support](https://learn.microsoft.com/en-us/sql/tools/sqlpackage/sqlpackage-download?view=sql-server-ver17), [SQL Server Linux support](https://learn.microsoft.com/sql/linux/install-upgrade/setup).

**Recommendation:** prefer an optional, explicitly provisioned Debian/Ubuntu x64 engine-worker profile instead of forcing Microsoft binaries into every Alpine/ARM image. The documented SqlPackage password/token arguments would place secrets in argv. No documented secure response-file solution was established in this research. A small DacServices helper reading a bounded request and secret via stdin is a viable design to verify; the official API accepts connection information in memory and exposes import/export plus cancellation tokens. Cancellation is explicitly not guaranteed to stop import, so preserve the blocked/interrupted state. [DacServices constructor](https://learn.microsoft.com/en-us/dotnet/api/microsoft.sqlserver.dac.dacservices.-ctor?view=sql-dacfx-162), [ImportBacpac](https://learn.microsoft.com/en-us/dotnet/api/microsoft.sqlserver.dac.dacservices.importbacpac?view=sql-dacfx-162), [ExportBacpac](https://learn.microsoft.com/en-us/dotnet/api/microsoft.sqlserver.dac.dacservices.exportbacpac?view=sql-dacfx-162).

**Source evidence:** the actual DacFx NuGet license is Microsoft Software License Terms, not the repository's MIT license. It grants distributable-code rights subject to conditions including significant primary application functionality, downstream protective terms, notices and other obligations. **Recommendation:** retain the artifact's terms/notices and make packaging/licensing an explicit decision; a repo badge is insufficient evidence for redistribution. Nothing was downloaded, installed or accepted during this task. [Package license](https://www.nuget.org/packages/Microsoft.SqlServer.DacFx/170.5.96/License).

## Agent interface: current MCP, OpenAPI and discovery

**Source evidence:** revision 2026-07-28 uses stateless self-contained requests and per-request capability negotiation. Tool listing may vary with request authorization and should be deterministic; the SDK should handle protocol framing rather than ad hoc JSON-RPC. [Core specification](https://modelcontextprotocol.io/specification/2026-07-28), [tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).

**Recommendation:** keep Elysia OpenAPI as the HTTP contract and the native SDK as the MCP protocol layer. Both invoke the same services and validation rules. Publish only supported domain operations: inspect capabilities, configure a connection/plan within scope, run backup, review restore, consume review/start restore, read/cancel job. Do not expose shell commands, arbitrary SQL or secret-read tools. A restore review should bind actor, artifact, target, expiry and relevant fingerprint, and start must recheck preconditions atomically. MCP hints and skills are guidance; enforcement belongs to services.

Current `server/mcp.ts` initially returned text JSON only and registered a fixed tool inventory. Add typed output schemas and structured content so agents do not parse prose. Keep a readable text representation for older hosts. The installed SDK release fixes a legacy structured-output wrapping behavior, so verify both modern and older clients during the later authorized protocol checks. [SDK release](https://github.com/modelcontextprotocol/typescript-sdk/releases/tag/v2.4.0).

**Source evidence:** the Tasks extension supplies durable handles with polling, cooperative cancellation and optional input requests. **Recommendation:** map it onto already durable Steelkeep jobs, with an explicit operation-status field preserving `interrupted` and validation details. A finished execution with an unknown domain outcome must not become an unqualified “successful restore” merely because the protocol task ended. Non-supporting clients keep receiving an accepted job and poll `get_job`. [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview).

**Source evidence:** Skills over MCP is a published extension with final SEP, but host/SDK coverage is still developing; reading a resource alone does not activate a skill. SDK 2.4.0 includes skill loading, while attachment remains experimental. **Recommendation:** publish one short secret-free playbook teaching capability checks, idempotency-key reuse, separate restore review/start, polling, interruption behavior and evidence interpretation. Salt's generated per-instance skill bundle is a useful interaction idea, but do not copy its broad workspace disclosure behavior or persist tokens/public secrets in the bundle. [Skills extension](https://modelcontextprotocol.io/extensions/skills/overview), [SDK release](https://github.com/modelcontextprotocol/typescript-sdk/releases/tag/v2.4.0).

**Source evidence:** HTTP authorization uses bearer headers, resource-bound tokens and authorization-server discovery. Tokens must not be placed in URI query strings. Client credentials is an optional machine-to-machine extension. **Recommendation:** do not copy Salt's token-in-address convenience. Keep named scoped installation tokens for the first private installation; when standard OAuth clients are required, integrate an established issuer and protected-resource metadata rather than labeling static bearer auth as full OAuth support. Bind audit records to server-verified actor IDs, not caller-supplied agent names. [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/index), [client credentials](https://modelcontextprotocol.io/extensions/auth/oauth-client-credentials).

**Recommendation:** keep the approved cool neutral/slate surfaces and blue/violet actions; follow the actual reference's page hierarchy, column density, secondary metadata and useful chart placement. Use scope/actor/last-used/revoke rows in agent settings and a copyable connection recipe. Present recovery evidence next to snapshots and operation logs instead of relying on badge color. A library migration does not provide this composition automatically.

Native `<dialog>` already provides a useful foundation. Ensure unique dialog labels, deliberate initial focus (least destructive action for risky steps), focus return and a visible close/cancel control. Accessibility requirements survive visual adaptation. React Aria and Base UI are reasonable future candidates for genuinely complex controls; neither needs to be installed to polish ordinary tables, buttons and native selects now. [W3C dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [React Aria quality](https://react-aria.adobe.com/quality), [Base UI releases](https://base-ui.com/react/overview/releases).

The initial activity chart already supplied a tabular data alternative. Preserve that if Chart.js is introduced to better match Databasement: Chart.js explicitly states that canvas content is not screen-reader accessible without added labeling/fallback. Keep dates/windows and loaded-history limitations visible; never chart recent 100 rows as if they were complete historical totals. [Chart.js accessibility](https://www.chartjs.org/docs/latest/general/accessibility.html).

## Self-hosting and acceptance priorities

**Recommendation:** separate web/API and worker trust boundaries; native engine binaries and restore credentials belong only in workers. Avoid a Docker socket in the application. Use allowlisted database/storage destinations with explicit private-network policy, per-service secret access, nonroot execution, private bounded temporary directories and process-group termination. A database backup product intentionally reaches private hosts, so a generic “block all private IPs” SSRF rule would break its purpose; restrict configured destinations deliberately instead.

Compose secret files are a practical fit with existing `*_FILE` configuration. Grant each secret only to services that need it, and do not assume a Compose bind-mounted secret file is encrypted at rest. Back up the metadata, encrypted connection state and encryption-key recovery material with deliberately separate access; losing the key makes encrypted credentials unusable. [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

Immutable artifact keys and create-only upload conditions reduce accidental overwrite but do not provide ransomware resistance if the same credential can delete everything. Optional object versioning/retention can help later, with retention-compatible cleanup and capability checks for the actual S3-compatible provider. AWS Object Lock applies to versioned objects; “S3-compatible” alone does not prove it exists or behaves identically. [AWS Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html).

When the user authorizes execution, prioritize checks that establish product facts: worker death during restore leaves target blocked; duplicate HTTP/MCP request returns the same job; dump/upload/download/restore preserves real fixture data; changing source data does not produce false validation; version mismatch and missing native tools fail before writes; secrets stay out of argv/responses/logs; and keyboard navigation works through review/start/cancel. All eight engine profiles require their own actual acceptance evidence. None was established by this research.

Skipped: no architecture rewrite, new dependency, runtime check, performance claim, deployment, production connection, or license acceptance. Remaining risk: native packaging, engine/topology coverage, OAuth interoperability and restore safety must be proven when execution is authorized.
