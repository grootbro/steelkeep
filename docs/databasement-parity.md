## This slice

Visual thesis: the same calm operational hierarchy as the reference's server profile—entity heading and actions, a narrow summary strip, working plans and snapshots, public connection facts alongside, recent jobs below. It uses existing Steelkeep surfaces and typography instead of adding a second design language.

Content and interaction: clicking a connection opens a real deep-linked profile with native back navigation. Plan and artifact actions call the existing application callbacks; source holds, permissions, request-key recovery and restore acknowledgement stay in force. A source, storage and restore destination each show relevant data, with correct empty states. Passwords, access keys and arbitrary config JSON are never rendered.

The profile uses current overview/jobs DTOs. Its snapshot and job summaries are explicitly bounded to the latest 100 records; it does not claim full-history aggregate totals. Backend pagination/aggregate gaps above are still required for full parity.

## API work needed next

1. Paginated/filterable `GET /connections`, `/plans`, `/backups`, `/jobs` plus per-connection aggregates and old-artifact lookup; preserve stable cursors and existing clients.
2. Snapshot download, comments and explicit single/bulk deletion beyond policy retention. Retention/locks now have owning services and selected native storage proof; broader provider/versioning and crash-boundary qualification remains.
3. Notification channel CRUD/test and durable terminal-event delivery, with hash/encrypted credentials and delivery history.
4. Per-server database discovery/selection, table exclusions and multi-volume publication with independent destination outcomes.
5. Reusable schedule management and scheduled restore semantics; an uncertain restore must retain a fenced target and never be replayed.
6. Remote execution agents/SSH, user roles/invitations and required authentication recovery/security flows.

No backend API is fabricated by this frontend slice. Full Databasement functionality remains incomplete until these owning services and their actual proofs exist.

## Validation of this frontend slice

Application `bun run typecheck` and `git diff --check` passed. An isolated Playwright context intercepted every `/api/v1/**` request with synthetic fixtures; it made no native backup or real account changes. It checked source/storage/target profile navigation, plan edit values, HEAD-only availability wording, backup request keys and job details, restore prepare/review/explicit acknowledgement/start and target-specific job association, read-only permissions, missing-connection recovery, and context-aware plan creation. A profile selects only its own source or storage; general plan creation keeps both choices empty.

Desktop (1440×1000) and mobile (390×844) layouts were inspected together. The mobile snapshot table was adapted to keep identity, size, availability and actions readable without horizontal page overflow. Screenshots are in `output/playwright/connection-profile-{desktop,mobile}.png`. These mocked UI checks validate wiring and presentation; they do not replace native engine qualification or full Databasement parity acceptance.
